# 공통 대화 게이트웨이

외부 메신저와 에이전트 시스템 사이의 연결부다. 핵심 대화 로직은 Telegram을 직접 참조하지 않는다.

```text
gateway/
├─ core/
│  ├─ models.py        공통 수신·발신 메시지
│  ├─ ports.py         채널·에이전트·Git 검사 인터페이스
│  ├─ security.py      사용자와 대화방 허용 정책
│  ├─ role_routing.py  이름·마지막 상대·전체 호출 선택
│  ├─ conversation.py  자유 대화·작업·프로젝트·승인 모드
│  ├─ application.py   중복 방지와 안전한 처리 진입점
│  └─ runner.py        폴링, 발신함 재시도, 커서 복구
├─ adapters/
│  └─ telegram/        첫 번째 실제 채널 어댑터
├─ conversation_worker.py 영속 대화 큐와 백그라운드 처리
├─ outbound_worker.py     비차단 발신함 전송 워커
├─ runtime_guard.py       게이트웨이 단일 실행 잠금
├─ config.py           비밀값과 일반 설정 로딩
├─ bootstrap.py        구성요소 조립
└─ cli.py              실행 진입점
```

역할 선택은 전체 호명(`얘들아`, `셋 다`, `모두`), 명시적 복수 응답 요청(`빌더랑 피니셔
둘 다 답해줘`), 문장 첫머리의 직접 호명, 마지막 대화 상대 순서로 결정한다. `모르면`,
`필요하면`, `~한테 물어봐`, `불러도 돼`, `말해도 돼`처럼 조건부 위임 문맥의 역할명은
최초 응답자를 바꾸지 않는다. 최초 역할은 원문 전체를 받고, 실제로 도움이 필요할 때만
구조화된 `calls`로 다른 역할을 후속 호출한다.

`얘들아`/`셋 다`의 첫 역할 답변은 `config/channels.json`의
`conversation.group_parallel_workers` 수만큼 병렬 실행한다. 기본값은 세 역할에
맞춘 3이다. 직접 호출 결과는 고정된 역할 순서로 정리하고, 에이전트가 다른
에이전트를 부르는 후속 대화와 명시적 복수 응답 호출은 앞 답변 문맥이 필요하므로
순차 실행한다. 형식·기술 재시도도 `max_auto_agent_replies`의 실제 모델
호출 4회 제한을 소비하고, 실행 직전에 토큰 예산을 다시 확인한다.

## 현재 가능한 일

- 프로젝트 없이 자유 대화 모드 시작
- 빌더·센티널·피니셔 이름 또는 전체 호명 해석
- 세 역할의 실제 Hermes 자유 대화와 역할 간 자동 상담 호출
- 메시지당 모델 답변 4회 제한과 반복 호출 차단
- 채팅별 마지막 대화 상대와 대화 모드 복구
- 대화방별 순서를 보장하는 SQLite 대화 작업 큐
- 공통·역할·사용자·프로젝트·작업 범위별 기억 저장
- 자유로운 에이전트 호출과 엄격한 작업 인계를 구분하는 계약
- 일반 문장으로 작업 요청 저장
- 매 작업마다 다른 Git 절대경로 선택
- 저장소별 정확한 `이 프로젝트 사용 승인해` 확인
- 버전·해시가 붙은 계획과 정확한 `개발 시작해` 승인 처리
- 채팅별 실행 상태와 대화 문맥 복구
- 허용된 사용자만 접근
- 수신 중복 제거와 실패 1회 재시도
- 긴 응답을 전송 전에 조각별로 보관해 부분 실패 중복 방지
- 실행기 임대가 있는 SQLite 발신함으로 다중 실행 중복 전송 방지
- Hermes 개발 담당과 승인 전 설계 대화
- 정확한 승인 뒤 파이프라인 작업 큐 등록
- 실행 상태 조회와 안전 중지 요청
- 실제 대화 백엔드 앞에서 토큰 사용량과 기술 재시도 강제
- 대화·상태 변경·오류 로그에서 비밀값 제거
- 같은 데이터 폴더의 게이트웨이 중복 실행 차단
- 대화·파이프라인 워커 생존 감시와 비정상 종료 전역 로그
- 전용 발신 워커를 통한 비차단 진행 알림과 장시간 작업 입력 상태 갱신
- 종료 시 활성 Hermes·검증 명령의 전체 하위 프로세스 트리 회수 후 단일 실행 잠금 해제

실제 구현은 `AgentConversationBackend`, `TeamConversationBackend`, `ConversationScheduler`, `PipelineScheduler` 포트 뒤에 있다. 따라서 게이트웨이는 Hermes나 Git 실행 세부사항을 직접 알지 않는다. 자유 대화의 호출은 상담일 뿐 담당권을 넘기지 않으며, 실제 작업 인계는 센티널의 분류에 따라 빌더 재작업·피니셔 구현 보완·보완 생략으로 분기한다.

## 다른 채널 추가

새 채널은 `ChatAdapter`의 `check`, `poll`, `prepare`, `send`를 구현한다. `prepare`는 채널별 길이 제한에 맞춰 발신 단위를 나눈다. 수신 메시지를 `IncomingMessage`로 변환하면 대화·승인·로그·상태 관리는 그대로 재사용된다.
